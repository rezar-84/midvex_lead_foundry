# Plan — MVX-020 white-label configuration and provisioning

**Tier:** 1 **Depends on:** MVX-019

## Problem

The product cannot be deployed for any organisation except Midvex: the brand name is
hardcoded in the header, TOTP issuer and crawler user-agent; the extraction
heuristics (product pattern, topic/role/sentiment/outcome/opportunity terms) are
Turkish/English regex constants compiled into `operations.py` and `pipeline.py`; the
synthetic fixtures and seed command embed `midvex.test`; and an organisation can only
be created through `/admin` or `seed_demo`.

## Outcome

A fresh install can be provisioned with one management command, carries its own brand
name, and extracts entities using per-project extraction profiles that default to the
shipped rules — with zero behaviour change for existing installs.

## Approach

1. **Branding via settings** (no schema): `FOUNDRY_BRAND_NAME` (default "Lead
   Foundry") and `FOUNDRY_USER_AGENT`, surfaced through the existing context
   processor; consumed in `templates/foundry/base.html`, the TOTP
   `issuer_name` (`foundry/views.py`), and the enrichment user-agent
   (`foundry/enrichment.py`). Package name stays `midvex-lead-foundry` (ADR 0008:
   package identity is not runtime brand).
2. **Heuristics → `ExtractionProfile`**: new `foundry/heuristics.py` holds
   `DEFAULT_FIELD_RULES` (the exact current regex strings) and compiles a validated
   `CompiledProfile` (regex errors → `ValidationError`; length/count caps against
   ReDoS). `active_profile(project)` returns the latest
   `ExtractionProfile(entity_type="message")` row or the shipped defaults — **no
   seeding migration**: the fallback makes seeded rows redundant and removes a
   drift/backfill risk (deviation from the original sketch, recorded in ADR 0008).
   `execute_sync_job`/`ingest_rfc822` and `execute_analysis_job` consume the
   compiled profile; `EnrichmentResult.extraction_profile_version` records the
   active version.
3. **Generic fixtures/seed**: synthetic messages move to neutral
   `demo.example.test` parties exported as constants; `seed_demo` gains
   `--org-name/--org-slug` (default `demo`); `LeadProjectForm` language choices come
   from `settings.LANGUAGES`.
4. **Locale scaffolding**: `DJANGO_LANGUAGE_CODE`/`DJANGO_LANGUAGES` env-driven;
   `LocaleMiddleware` added. `{% trans %}` sweep stays deferred (MVX-023).
5. **Provisioning**: management command `provision` — org + admin user + admin
   membership, idempotent, password from `FOUNDRY_ADMIN_PASSWORD` or interactive
   prompt, never echoed. A first-run web wizard is rejected (unauthenticated attack
   surface); revisit under MVX-014.

## Alternatives rejected

| Option | Why not |
| --- | --- |
| Organization-level brand field (schema) | One deployment = one brand for self-hosting; a column adds migration surface with no consumer until MVX-014. |
| Seed a default profile row per project + backfill migration | Redundant with code fallback; seeded copies of defaults drift when defaults improve, and deleting them is a data migration. |
| Web setup wizard | New unauthenticated surface on a security-sensitive product; CLI is auditable and scriptable. |

## Affected surfaces

- **Code:** `lead_foundry/settings.py`, `foundry/heuristics.py` (new),
  `foundry/operations.py`, `foundry/pipeline.py`, `foundry/enrichment.py`,
  `foundry/connectors.py`, `foundry/views.py`, `foundry/context_processors.py`,
  `foundry/forms.py`, `foundry/management/commands/{seed_demo,provision}.py`,
  `templates/foundry/base.html`.
- **Data:** none — no migration; `ExtractionProfile` rows are created only by
  explicit override.
- **Contracts:** `EnrichmentResult.extraction_profile_version` now reflects the
  active profile version (was constant 1 — same value for defaults).
- **Docs to update:** README (self-hosting), `data-model-api.md`, `.env.example`,
  ADR 0008, backlog, worklog.

## Failure modes

Invalid profile rules → `ValidationError` at compile, job fails with a clear error
code rather than applying partial rules; missing env vars → shipped defaults (no
behaviour change); `provision` re-run → idempotent update, never resets an existing
password; hostile regex in `field_rules` → length/count caps + compile validation.

## Test strategy

- **Unit:** default rules reproduce current extraction on the synthetic fixtures
  (parity); invalid `field_rules` rejected; per-project override changes extraction
  output; brand name and TOTP issuer render from settings.
- **Integration:** `provision` idempotency and no-secret-echo;
  enrichment records the active profile version.
- **Negative cases:** malformed regex, oversized pattern, non-string rule values,
  re-provision with existing user.
- **Manual:** none required beyond the seeded runserver smoke (recorded if run).

## Rollback

All defaults reproduce pre-change behaviour; unset the new env vars and the install
is indistinguishable from before. No migration to reverse. Profile overrides are
plain rows — deleting them restores shipped defaults.

## Out of scope

Profile editor UI (follow-up noted in backlog); `{% trans %}` sweep (MVX-023);
multi-tenant brand/config (MVX-014); retention purge (MVX-022).

## Assumptions

Single-deployment/single-brand assumption holds until MVX-014.
